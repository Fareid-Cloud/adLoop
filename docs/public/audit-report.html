🔴 Critical Findings

Critical Finding #1 — CSP Allows 'unsafe-inline' 'unsafe-eval'

File:

next.config.js lines 55-56

Code:

"script-src 'self' 'unsafe-inline' 'unsafe-eval' https://challenges.cloudflare.com",
"style-src 'self' 'unsafe-inline'",

What is wrong:

The Content-Security-Policy includes both 'unsafe-inline' and 'unsafe-eval' for scripts. This completely neutralizes CSP as an XSS defense — any injected <script> tag will execute freely.

Why it is wrong:

CSP is supposed to be the last line of defense against XSS. With these flags, an XSS vulnerability anywhere in the app (including AI-generated markdown content) gives an attacker full script execution.

Real-world impact:

If any input is reflected without proper sanitization, an attacker can steal session cookies, admin tokens, or OAuth tokens.

How to reproduce:

Inspect response headers on any page — the CSP header contains unsafe-inline and unsafe-eval.

Recommended fix:

Use nonce-based CSP for inline scripts. Next.js supports this via dynamic nonces. Remove 'unsafe-eval' entirely.

Critical Finding #2 — No Rate Limiting on OAuth Login Callbacks

Files:

app/api/oauth/login-google/callback/route.ts, app/api/oauth/login-facebook/callback/route.ts

What is wrong:

Both OAuth login callbacks create sessions without any rate limiting. The email/password login has IP-based rate limiting (10/15 min), but OAuth login has none.

Why it is wrong:

This creates an inconsistency where the weaker path (OAuth) is the unprotected one. An attacker with a valid OAuth code can create unlimited sessions.

Real-world impact:

Session creation flooding, potential account abuse.

How to reproduce:

Call POST /api/oauth/login-google/callback repeatedly with valid codes.

Recommended fix:

Add rate limiting to OAuth callback endpoints, at minimum per-IP.

Critical Finding #3 — OAuth Account Linking Allows Silent Account Takeover

Files:

app/api/oauth/login-google/callback/route.ts, app/api/oauth/login-facebook/callback/route.ts

Code:

const existingByEmail = await prisma.user.findUnique({ where: { email: profile.email } });
if (existingByEmail) {
  user = await prisma.user.update({
    where: { id: existingByEmail.id },
    data: { googleLoginId: profile.sub, ... },
  });
}

What is wrong:

If a user signs up with email/password, an attacker who controls that email on Google can log in via OAuth and the code will automatically link the attacker's Google ID to the existing account. No consent is required from the original account holder.

Why it is wrong:

The OAuth flow trusts the email from Google's profile without verifying that the original account holder linked their Google account. Anyone with access to an email address on Google can claim it.

Real-world impact:

Account takeover. An attacker creates a Google account with a victim's email, then uses Google OAuth to gain access to the victim's AdLoop account.

How to reproduce:

  1. Create AdLoop account with victim@example.com + password.
  2. Create Google account with victim@example.com.
  3. Use Google OAuth login — the code links the Google ID to the existing account and issues a session.

Recommended fix:

When linking an OAuth provider to an existing email/password account, require the user to be logged in first and confirm the linking explicitly. Do NOT auto-link on email match.

🟠 High-Risk Findings

High Finding #4 — Rate Limiter Fails Open Under DB Pressure

File:

lib/rateLimit.ts

Code:

} catch (err) {
  console.error("فشل فحص حد الاستخدام:", err);
  return { allowed: true, remaining: maxRequests };
}

What is wrong:

When the database is unreachable or slow, the rate limiter defaults to allowing all requests ("fail open"). Under a DDoS or database outage, rate limiting disappears exactly when it's most needed.

Real-world impact:

During database issues, all rate-limited endpoints (login, signup, CTA tracking, password reset) become unprotected.

Recommended fix:

Use an in-memory rate limiter as a fallback when DB is unavailable, or set a hard ceiling on concurrent requests.

High Finding #5 — GAQL Queries Use String Interpolation for Campaign IDs

File:

lib/syncGoogleAds.ts (multiple locations)

Code:

WHERE segments.date BETWEEN '${from}' AND '${to}'
  AND campaign.id IN (${campaignIds.join(",")})

What is wrong:

Campaign IDs and date ranges are interpolated directly into GAQL query strings. While IDs come from the database, if a malicious workspace owner crafted campaign link records with specially crafted IDs, they could inject GAQL syntax.

Real-world impact:

Potential unauthorized data access from Google Ads API, or garbled queries returning incorrect data.

Recommended fix:

Validate campaign IDs against a strict pattern (e.g., /^\d+$/) before interpolation.

High Finding #6 — Meta Messenger Webhook Missing Idempotency

File:

app/api/webhooks/meta-messenger/route.ts

What is wrong:

Unlike Salla and Shopify webhooks which use markEventAsProcessed for idempotency, the Meta Messenger webhook has no deduplication. Meta can redeliver webhooks, and the code will process them again.

Real-world impact:

Inflated message counts, potential double-counting of verified conversions, incorrect response time metrics.

How to reproduce:

Trigger the same Meta webhook event twice — messageCount increments twice.

Recommended fix:

Add a unique message ID or timestamp-based deduplication using ProcessedWebhookEvent.

High Finding #7 — Paymob HMAC Field Order Is a Guess

File:

app/api/webhooks/paymob/route.ts

What is wrong:

The HMAC verification field order is a guess based on old Paymob documentation. If the order is wrong, ALL payment webhooks will be rejected (fail closed), meaning subscriptions will never activate after payment.

Real-world impact:

Users who pay will never have their subscriptions activated. Revenue loss.

Recommended fix:

Confirm field order from Paymob dashboard (Settings → Payment Integrations → HMAC). Add monitoring alert when ALL webhook verifications fail.

High Finding #8 — $queryRawUnsafe in Health Endpoint

File:

app/api/health/schema/route.ts

Code:

const rows = await prisma.$queryRawUnsafe<...>(
  `SELECT table_name, column_name
   FROM information_schema.columns
   WHERE table_schema = current_schema()`
);

What is wrong:

While the specific query has no user input, using $queryRawUnsafe is a dangerous pattern. Any future modification that adds user input would create a SQL injection vulnerability.

Recommended fix:

Replace with $queryRaw with tagged template literals.

File:

middleware.ts

What is wrong:

The middleware only checks if the session cookie exists, not if it's valid. An expired or tampered cookie passes middleware and only fails at the route handler level.

Real-world impact:

Minor performance waste. Security is maintained by route-level checks.

Medium Finding #10 — Missing CSRF on Many Mutation Endpoints

What is wrong:

CSRF protection is on admin routes (impersonate, suspend, reauth) but missing on workspace creation, product updates, campaign link changes, and other mutation endpoints.

Real-world impact:

An attacker could craft a page that makes authenticated users unknowingly modify their data.

Medium Finding #11 — OAuth Login Doesn't Check isSuspended Before Linking

What is wrong:

The isSuspended check happens after the account is linked/linked. The database write succeeds even for suspended users.

Medium Finding #12 — getEntitlements Called Too Frequently Without Caching

File:

lib/entitlements.ts

What is wrong:

getEntitlements makes a database query every time it's called. It's invoked from multiple places per request — potentially 10+ DB queries for entitlement checks alone.

Recommended fix:

Cache entitlements per-request using AsyncLocalStorage or pass through request context.

🔵 False Positives & Uncertain Findings

Info SQL Injection via Prisma

Prisma uses parameterized queries by default. The only raw query ($queryRawUnsafe in health check) has no user input. Not a vulnerability.

Info child_process in Build Scripts

Only used in scripts/*.mjs build scripts, not in runtime code. Not a vulnerability.

Info Hardcoded JWT Secret in Comments

Comments reference JWT_SECRET but it's always read from process.env. Not a vulnerability.

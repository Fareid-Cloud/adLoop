1. Executive Summary & Readiness Verdict

A comprehensive, non-destructive, full-system production readiness audit was performed across all 186 API routes, 144 library modules, Prisma database schemas, cron pipelines, AI cost controls, and payment fulfillment logic of AdLoop SaaS.

Final Verdict: CONDITIONALLY READY (Launch Blockers Identified)

The codebase exhibits commendable engineering rigor in core security practices: OAuth tokens and MFA secrets are properly encrypted via AES-256-GCM, multi-tenant workspace queries are centralized via workspaceAccess, cross-origin write CSRF guard is enforced in middleware.ts, timing-safe authentication mitigates email enumeration, and AI quotas are protected by atomic SQL updates.

However, two P0 critical blockers in the billing/webhook domain and three P1 high-severity reliability risks in the tracking and serverless cron pipelines prevent a safe, public launch to paying customers in their current state.

5. Detailed Evidence-Based Audit Findings

[FINDING-P0-01] Paymob Webhook HMAC Field Order Ambiguity & Incomplete Header Lookup
P0 • CRITICAL app/api/webhooks/paymob/route.ts#L22-L60

Category: Billing, Payments & Webhooks • Confidence: 100% (Confirmed in Code & Gotchas)

Root Cause

The HMAC signature verification relies on a hardcoded string array HMAC_FIELD_ORDER that was inferred from legacy Paymob documentation rather than verified against live Paymob API v1 transactions. Additionally, the route only inspects searchParams.get("hmac") without checking request headers (x-paymob-hmac) or body payload attributes.

Failure Scenario

A customer initiates checkout and successfully completes payment on Paymob. Paymob dispatches a webhook event. Because the field concatenation order differs or HMAC is sent in request headers, verifyPaymobHmac() returns false. AdLoop responds with HTTP 401. The transaction status remains PENDING in the database, and the customer's subscription plan is never activated.

Customer & Financial Impact

Immediate customer dissatisfaction, customer support overload, lost revenue, and payment dispute/chargeback risks.

Recommended Fix

Perform live sandbox transactions with Paymob; verify exact HMAC hashing fields; read HMAC from both req.headers.get("x-paymob-hmac") and query string; log unverified payload structures safely in staging.

[FINDING-P0-02] Absence of Automated Recurring Billing & Dunning Engine
P0 • CRITICAL lib/billing.ts#L338-L358, lib/entitlements.ts#L93-L126

Category: Subscriptions & Entitlements • Confidence: 100%

Root Cause

When a customer subscribes, currentPeriodEnd is set to 30 days in the future. However, no cron worker exists to trigger recurring token charges against user.savedCardToken via Paymob's Intention / Token API before or on expiration.

Failure Scenario

After 30 days, user.currentPeriodEnd > now evaluates to false. getEntitlements() immediately drops the subscriber to the FREE tier. Ad accounts above 1, multi-platform sync, conversion sync, and automated rules are instantly locked out without any automated charge attempt.

Customer & Financial Impact

100% churn of paid subscribers after their initial billing cycle. Complete breakdown of SaaS revenue model.

Recommended Fix

Implement app/api/cron/billing-renewals/route.ts to scan users whose currentPeriodEnd is within 48 hours and invoke Paymob token charge. Provide a 3-day grace period with email notifications prior to downgrading features.

[FINDING-P1-01] Local Server Timezone Skew Drops WhatsApp & Messenger Verified Conversions
P1 • HIGH app/api/attribution/mark-matched/route.ts#L61-L75, lib/messengerLeadQuality.ts#L144-L153

Category: Tracking, Attribution & Data Integrity • Confidence: 100%

Root Cause

mark-matched/route.ts computes dayStart = new Date(receivedDate.getFullYear(), receivedDate.getMonth(), receivedDate.getDate()). In JavaScript, this constructor evaluates to local server midnight (e.g. 21:00:00.000Z in UTC+3). However, ad platform sync scripts (syncGoogleAds, syncMetaAds) create MetricSnapshot.date at exact UTC midnight (00:00:00.000Z).

Failure Scenario

When a WhatsApp conversation is matched or Messenger lead is verified on a server with non-UTC local time, prisma.metricSnapshot.updateMany searches for date: dayStart, matches 0 rows, and exits cleanly. The verified conversion count on the daily metric snapshot is never incremented.

Customer & Financial Impact

The core value proposition of AdLoop ("The Truth Layer") shows zero verified conversions despite real customer sales occurring.

Recommended Fix

Consistently normalize all snapshot date queries to UTC midnight using: new Date(receivedDate.toISOString().slice(0, 10)).

[FINDING-P1-02] Monolithic Daily Sync Cron Exceeds Vercel Serverless Function 300s Limit
P1 • HIGH app/api/cron/sync-google-ads/route.ts#L173-L265

Category: Scalability & Background Reliability • Confidence: 100%

Root Cause

sync-google-ads/route.ts iterates sequentially across every workspace in the system, executing ~35 API calls per workspace. At 15+ workspaces, total duration surpasses Vercel Pro's hard 300-second execution cap.

Failure Scenario

Vercel issues a SIGKILL to the serverless function. Workspaces remaining in the queue are never synchronized, captureUsageSnapshots() is skipped, and CronRunLog is never recorded.

Customer & Financial Impact

Stale data on customer dashboards, unexecuted automation rules, and incomplete daily audit reporting.

Recommended Fix

Implement chunked execution (e.g. batch size of 5 workspaces with continuation tokens) or dispatch asynchronous per-workspace background tasks.

[FINDING-P1-03] Conflicting Dual Salla Webhook Routes with Data Desynchronization
P1 • HIGH app/api/webhooks/salla/route.ts vs app/api/webhooks/ecommerce/[platform]/route.ts

Category: E-commerce Integrations & Data Consistency • Confidence: 100%

Root Cause

Two separate Salla webhook handlers exist in the repository. The legacy handler (app/api/webhooks/salla/route.ts) uses a single global secret SALLA_WEBHOOK_SECRET, writes to campaignId: "unlinked", and completely bypasses EcommerceConnection, Customer records, customer cohorts, and inventory stock tracking.

Failure Scenario

Merchants configuring Salla with the legacy URL experience partial data ingestion, missing store funnel analytics, and bypassed stock guard alerts.

Customer & Financial Impact

Inconsistent e-commerce metrics and merchant confusion.

Recommended Fix

Remove the legacy route or forward requests from /api/webhooks/salla to the unified ecommerce adapter.

[FINDING-P2-01] Missing Purchased Credit Refund on Failed AI Chat Invocations
P2 • MEDIUM app/api/ai/chat/route.ts#L110-L115, lib/aiRateLimit.ts

Category: AI Cost & FinOps • Confidence: 100%

Root Cause

When Claude API throws an upstream error, app/api/ai/chat/route.ts decrements aiRefreshMonthlyCount directly in Prisma, but does not reset aiChatHourlyCount and fails to increment aiCreditsPurchased if a purchased credit was deducted by consumePurchasedCreditIfNeeded.

Failure Scenario

A user with purchased AI credits asks a question during an Anthropic service disruption. The request fails with HTTP 502, but their purchased credit is permanently forfeited.

Recommended Fix

Create a dedicated refundChatQuota(userId) function in lib/aiRateLimit.ts that reverses both hourly counters and purchased credit deductions.

[FINDING-P2-02] Google Ads Conversion Action Resource Name Formatting Vulnerability
P2 • MEDIUM lib/conversionSync.ts#L280-L283, app/api/workspaces/[id]/route.ts

Category: Ad Platform Integrations • Confidence: 95%

Root Cause

ResourceNames.conversionAction(link.externalAccountId, workspace.googleConversionActionId) expects a numeric string ID. If a user pastes the full resource name (e.g. customers/123/conversionActions/456), it produces a doubled malformed path.

Failure Scenario

Google Ads API rejects all offline conversion upload requests with an INVALID_CONVERSION_ACTION error.

Recommended Fix

Sanitize googleConversionActionId upon save or in conversionSync.ts using actionId.replace(/^.*conversionActions\//, "").replace(/\D/g, "").

[FINDING-P2-03] DNS Resolution Edge Case in SSRF Guard (safeFetch)
P2 • MEDIUM lib/safeFetch.ts#L29-L46

Category: Security & Defense in Depth • Confidence: 90%

Root Cause

assertPublicHost() calls dns.resolve(hostname).catch(() => []). If DNS resolution encounters a timeout, error, or resolves exclusively via IPv6, the loop completes without throwing. The subsequent fetch() resolves DNS independently, creating a TOCTOU (Time-of-Check to Time-of-Use) window.

Recommended Fix

Explicitly resolve both IPv4 and IPv6 records and pin the resolved IP address in the HTTP dispatcher.

[FINDING-P3-01] Legacy Hardcoded Strings & Dialect Inconsistencies in Backend Throws
P3 • LOW lib/paymob.ts#L50, lib/safeFetch.ts#L33,L43,L58,L83,L95

Category: Localization & Brand Consistency • Confidence: 100%

Root Cause

Several throw statements in core libraries contain Egyptian Arabic dialect or unlocalized text instead of Standard Arabic / English dictionary keys.

Recommended Fix

Wrap library errors in standard error keys or pass localized dictionary strings via t(locale, ...).
